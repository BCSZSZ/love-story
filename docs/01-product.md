# 01｜产品需求基线

版本：2.0.0 · 日期：2026-09-28 · 默认工作名：东京·爱情故事 · 工程名：tokyo-love-story。

本文是当前产品基线；第一轮变更的详细业务、工作簿与迁移口径见 `docs/10-first-round-change-spec.md`。产品仍是匿名择偶条件估算器，不是真实婚介、人物库或推荐服务。所有人口、比例、评分和圈层数字都必须标为演示配置。

## 1. 产品目标

让成年人逐项填写自身情况、设置对另一半的条件，并理解多项条件叠加后候选规模如何变化。系统同时展示：

1. 所选真实城市内、满足条件的“同城条件池”。
2. 在用户选择的可触达圈层及助力范围内、满足相同条件的“圈层内可达”。

系统不展示真实人物，不做匹配推荐，不根据评分判断“配不配”。分数与人数独立；自身和对方要求继续使用同一个评分函数。未来双向接受度仍为 `not_implemented`。

## 3. 计算边界

- 匹配城市是全局必选输入，不是可设为“无要求”的问题，也不接受强度调整。
- 一个条件原始覆盖率为 `p`、强度为 `s` 时，有效覆盖率为 `e = 1 - s × (1 - p)`。因此 1 为完整排除，0 为完全放宽。
- “同城条件池”先应用成年人和城市质量，再乘所有有效条件覆盖率。
- “圈层内可达”使用同一组条件覆盖率乘有效可触达规模；不是从同城条件池再次过滤，也不是两个结果相乘。
- 助力增幅相对于基础圈层相加：`effectiveReach = min(cityAdultBase, tierPeople × (1 + Σ boostRate))`。
- 相对条件缺少自身值时产生可定位 issue，结果标为阶段性；不得把缺失值当 0 或悄悄忽略后宣称完成。

## 4. 问题、配置与版本

“问题/字段”是一条独立填写和计算的条件维度，例如年龄、学历、年收入；“选项”是该问题下的答案。v2 种子含 62 个普通问卷问题，加上顶层 `matchCityId`，但 62 不是永久上限。

后台由运行时配置驱动，可新增互斥枚举、数值/区间、独立标签三类问题。尚未发布的新问题可以物理删除；发布过的问题只能在新版本标记 `retired`。已发布 ID 和类型不能原地改写或复用。前端、共享引擎、服务端复算和 Excel 必须读取同一配置包。

每次发布生成不可变 `configBundleVersion`，并绑定目录、模型和汇率版本及规范化 checksum。新测试取当前激活版本；已开始草稿固定原版本。回滚只切换激活指针，不改写历史配置。

## 5. 数据与信息最小化

匿名记录只收结构化答案、要求、城市、圈层、助力、配置版本及必要技术元数据。不收姓名、昵称、电话、邮箱、照片、精确地址、雇主名称、证件、账户明细、病历或自由长文本；不根据 IP 猜地区，不做设备指纹或分析追踪。

匿名记录以本机随机管理凭据修改或删除；没有公开读取/list 接口。管理员 Cognito 身份只用于配置审计，后台执行角色不拥有匿名记录表权限。管理员密码、token、授权码、完整 claims 和匿名答案均不得进入日志。

## 6. 明确排除项

不做真实人物匹配、公开画像、普通用户账号、聊天、排行榜、收费、支付、AI 颜值、照片上传、LLM 计算、实时人口/汇率、自动星座合盘、自动推断生肖、云端保存分享图片、后台查看匿名答卷、任意脚本/公式上传。首轮不要求 MFA；以后启用必须另行决策。

## 7. 完成状态的用词

必须区分设计完成、实现完成、mock 通过、真实 AWS 服务验证和线上验证。当前代码完成及本地验证不等于已部署；没有真实账户、回调 URL、diff 和明确部署授权时不得创建云资源或报告线上完成。
