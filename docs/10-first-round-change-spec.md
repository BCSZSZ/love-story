# 10｜第一轮需求变更式样（确认版）

状态：`CONFIRMED / 2026-09-28 已授权实装`  
日期：2026-09-28  
适用基线：当前已发布的 `catalog-demo-1.0.0`、`model-demo-1.0.0` 与匿名一年保存机制。

> 本文定义已确认需求与验收口径。用户已授权本地实装与 Git 推送，但未授权 AWS 部署；实现、mock、真实服务与线上验证仍须分别报告。

## 1. 本轮目标

本轮包含四项互相关联的变更：

1. 将“现居地”从普通问卷字段提升为全局必选的“匹配城市”，并用它动态生成“XX·爱情故事”标题；估算始终只在双方同城的范围内进行，用户可选项只允许真实城市。
2. 增加只有管理员需要登录的配置后台；普通用户继续匿名使用。后台可管理条件选项、演示比例、评分映射，以及本轮新增的同城、可触达圈层、助力项和五档放宽配置。
3. 在完整结果页增加“可触达圈层”维度，用个人可触达人群规模估算现实社交范围内可能遇到的人数，并允许叠加朋友、家庭、相亲服务等助力。
4. 将现有“单项放宽”增强为每个已设置条件都可选择五档约束强度，并支持预览后再应用。

本轮继续遵守以下边界：

- 产品仍是匿名条件估算器，不是真实婚介、人物库或推荐服务。
- 普通用户不注册、不登录；匿名记录仍使用本机管理凭据，首次云端创建后固定保存一个公历年。
- 不新增姓名、邮箱、电话、照片、精确地址、自由文本、设备指纹或公开记录读取。
- 自身分与对方要求分继续使用同一个评分函数；评分与人数估算继续分离。
- 所有数字继续标明为演示配置，不声称是真实人口统计或真实社交图谱。
- 除“现居地”迁移和五档约束强度外，其余条件的字段含义、控件、AND/OR、相对条件及当前过滤算法保持不变。
- 本轮后台只管理模型配置，不查看、搜索、导出或统计匿名用户答卷。

## 2. 对现有基线的明确变更

| 现有基线 | 本轮变更 |
|---|---|
| `residence` 同时有“我的情况”和“对方要求” | 删除这张问卷卡，改成全局单选 `matchCityId`；一个真实城市同时代表双方现居城市 |
| 所有要求只有“有要求/无要求” | 增加 1.0、0.8、0.6、0.4、0.0 五档约束强度 |
| 结果人数是全球成年人基数经过字段连乘后的规模 | 先得到同城条件池，再得到个人可触达圈层内的估算规模 |
| 结果页自动生成离散的单项放宽方案 | 改为每个已设置条件可调五档，并保留“影响最大的三项”快捷建议 |
| 首版没有管理后台、Cognito | 增加配置后台与管理员专用 Cognito 登录 |
| 配置随前后端构建发布 | 改为后台发布不可变、可回溯的运行时配置版本 |

这两项旧边界将被新需求显式取代：`FR-05` 的“无软性档位”与 `FR-16` 的“无管理后台”。其他旧边界不因本轮需求自动失效。

## 3. 统一术语

为避免“城市”“社交圈”“系数”在页面和算法中各指不同含义，本轮统一使用以下名称：

| 中文名称 | 建议代码名 | 定义 |
|---|---|---|
| 匹配城市 | `matchCity` | 普通用户选择的一个真实城市，同时代表自己与候选人的现居城市；只应用一次人口比例 |
| 同城条件池 | `cityCandidatePool` | 选定匹配城市的成年人中，经过各条件约束后的演示候选规模 |
| 可触达圈层 | `reachTier` | 用户在该匹配城市内可直接或间接触达的成年人演示规模，不是好友数或平台真实用户数 |
| 助力项 | `reachBoost` | 对基础可触达规模增加固定比例的可选开关 |
| 问题（字段） | `field` | 一条可独立填写、配置和计算的条件维度，例如年龄、学历、年收入；选项是问题下面的可选答案，不是字段本身 |
| 有效可触达规模 | `effectiveReach` | 基础圈层叠加所有已开助力后的规模，并以匹配城市成年人规模为上限 |
| 圈层内候选 | `reachableCandidateCount` | 有效可触达人群中，按相同条件覆盖率估算的候选规模 |
| 约束强度 | `strictness` | 某项条件排除不符合者的程度；1 为完全执行，0 为不执行 |
| 配置包 | `configBundle` | 同一次发布的一组目录、比例、评分、圈层、助力与放宽档位版本 |

页面文案避免把用户本人称为“普通人”“社交大牛”等带评价色彩的身份；圈层名称描述覆盖范围，不评价人的价值。

## 4. 匹配城市与动态标题

### 4.1 产品行为

- 首页标题格式为 `{titleLabel}·爱情故事`，初始建议为 `东京·爱情故事`。
- 标题旁提供单选的匹配城市切换入口；首页、填写页与结果页都可进入切换。
- 新建测试必须有且只有一个 `matchCityId`。建议初始默认值为 `jp_tokyo`，但必须在首页清楚展示，不能后台静默决定。
- 用户可见列表只包含真实城市，例如东京、上海、北京、大阪；不得把省、都道府县组合、大区或“其他地区”作为可选城市。
- 该值同时表达“我现居于此”和“只估算同一城市的候选人”，普通问卷中不再出现“现居地”卡片。
- 匹配城市不是可以设为“无要求”的普通条件，不能在结果页通过约束强度放宽，也不能多选。
- 用户切换匹配城市时，其他已填答案、条件、圈层和助力保持不变，系统立即重算并正常保存。
- 分享卡、结果页、保存快照和计算 trace 都显示所选匹配城市及配置版本。

### 4.2 字段迁移

- 新目录版本中，原 `residence` 不得保留为隐藏控件、固定 `p=1` 字段或重复筛选项。
- 初始 v2 种子保留其余 62 个原有问题；`matchCityId` 成为快照顶层的第 63 个实质输入维度，而不是 `own`/`requirements` 中的普通字段。管理员以后可发布新增问题，因此 63 只描述初始迁移数量，不再是永久上限。
- 原 `residence` 中确属真实城市的演示人口质量迁入城市配置，作为 `matchCity` 的人口比例来源；原有省、大区和复合区域不能直接变成用户可选城市。
- 城市 ID 必须稳定；展示名、标题短名和排序可由管理员修改。已被历史版本引用的 ID 不物理删除，只能在新版本停用。
- 为维持全球演示基数的质量守恒，模型内部可以有不可选的 residual 质量桶；它只是计算余量，不是用户可选的“其他城市”。全部用户可选项仍必须是真实城市。

### 4.3 老草稿与老记录

- 云端现有 v1 快照不批量改写，继续按原配置保留至到期。
- 本机 v1 草稿首次由新版打开时保留全部非地域答案：
  - 原自身现居地与对方现居地均为同一个单一叶子区域时，可预选该区域，但仍显示一次迁移确认。
  - 只有一侧存在单一叶子区域时，可用它作为建议值，但不能伪称已确认双方同城。
  - 两侧不一致、对方为多选/大区预设或值已停用时，必须让用户重新选择匹配城市；不得静默回落到东京。
- 用户确认匹配城市前，旧草稿可以浏览和修改，但不能标为“完成”或上传成 v2。
- 转成 v2 后保留原 `recordId` 和本机管理凭据；下一次成功保存才把该记录更新为 v2，失败时仍明确显示失败。

## 5. 管理后台

### 5.1 入口与角色

- 建议路由：`/#/admin`；普通页面不突出展示管理员入口。
- 普通用户页面和匿名记录 API 不要求 Cognito token，行为保持不变。
- 管理员使用 Amazon Cognito User Pool 的托管登录页，采用 Authorization Code + PKCE。
- Cognito 关闭自助注册，只允许人工邀请或管理员创建账户；首版不要求 MFA。
- 不启用 MFA 时仍要求强密码、首次登录更改临时密码、合理的 token 有效期、登录失败限速和最少管理员账户；以后需要时可单独启用 MFA，不改变普通用户匿名机制。
- API Gateway 对 `/api/admin/*` 使用 JWT authorizer，并要求管理员访问 scope；Lambda 仍二次校验必要 claims。
- 首版只有 `config-admin` 一个角色：查看、编辑、导入、导出、验证、发布和回滚配置。暂不增加复杂权限矩阵。
- 管理员 token、授权码、密码和完整 claims 不写入应用日志。

采用上述方案的依据是 Cognito 官方支持托管登录与 Authorization Code + PKCE，API Gateway HTTP API 可用 JWT authorizer 校验 issuer、audience 和 scope：

- [Amazon Cognito：PKCE authorization code grant](https://docs.aws.amazon.com/cognito/latest/developerguide/using-pkce-in-authorization-code.html)
- [API Gateway：HTTP API JWT authorizer](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-jwt-authorizer.html)

### 5.2 后台页面

后台至少包含以下五个一级页面：

1. **配置概览**：当前线上版本、草稿版本、发布时间、发布人、校验状态、checksum。
2. **条件管理**：按九个现有分组搜索和筛选字段，编辑展示名、选项、预设端点、演示比例与评分映射。
3. **城市与圈层**：编辑匹配城市、默认城市、圈层档位及助力项。
4. **放宽档位**：编辑五档名称与系数，查看单调性校验结果。
5. **导入、导出与发布**：下载模板/指定版本、导入预检、差异预览、保存草稿、发布和回滚。

所有写操作都显示“尚未发布”“发布中”“发布成功”或明确失败状态；前端本机成功不能冒充服务端已发布。

### 5.3 什么是“字段”以及新增/删除问题

本文中的“字段”就是用户看到的一道问题或一个条件维度。例如：

- “年龄”是一个数值字段；“25～35 岁”是该字段的一条要求。
- “学历”是一个枚举字段；“本科、硕士、博士”是它的选项。
- “爱好”是一个标签字段；“旅行、阅读、运动”是它的标签选项。

因此，“新增字段”就是新增一道完整问题，不是只给现有问题加一个答案。该需求现已确认纳入后台：管理员可以新增问题，也可以让已有问题从新版本中下线。

为保证新增问题无需每次重新写代码，前端表单、共享引擎、服务端校验和 Excel 都必须改成由运行时目录驱动，不能继续把 63 个 `FieldId` 固定写死在 TypeScript union 中。新增问题至少需要同时配置：

- 不可重复且发布后不可改名的 `fieldId`、中文题名、所属分组和排序。
- 问题类型、我的情况控件、对方要求控件与允许的运算符。
- 选项或数值范围、预设条件、演示人口分布。
- 是否敏感、是否计分；若计分则必须提供唯一一套双方共用的评分定义。
- 初始启用状态及必要的说明文案。

首轮提供三类安全模板：互斥枚举、数值/区间、独立标签；允许这些模板支持现有的单选、多选、门槛、区间与 `any_of`。管理员不能上传 JavaScript、公式代码或 HTML。跨字段相对条件只能引用一个已存在且兼容的数值字段，并使用系统支持的比较方式；不开放任意脚本依赖。

“删除问题”分两种：

- 尚未发布的新问题可以从当前草稿中真正删除。
- 已经发布过的问题只能在新配置版本中标记为 `retired`，从新测试中消失；历史配置和未过期快照仍保留其定义，不能物理抹除或改用同一 ID 表示另一道题。

管理员新增、停用或恢复问题都必须经过完整预览、服务端校验和新配置包发布。任何 active 问题都不能缺少控件或分布，也不能用固定 `p=1` 冒充实现。

### 5.4 可编辑范围

管理员可编辑：

- 新增问题，以及停用、恢复、重命名和排序既有问题；已发布 `fieldId` 与数据类型不可原地改写。
- 字段与选项的中文展示名、分组、排序和启用状态。
- 枚举选项、标签选项、数值桶、固定预设、相对预设。
- 枚举人口质量、标签 prevalence、数值桶质量。
- 12 个现有可评分字段的分值映射/折点与权重；自身和对方仍共用同一份评分函数。
- 匹配城市的 ID 以外属性、人口质量、启用状态、默认项与不可选 residual 质量。
- 可触达圈层、助力项、五档约束强度。

首轮后台不允许：

- 改变一个已发布字段的数据类型、复用历史 `fieldId` 表达新含义、改变运算符语义或上传自定义执行代码。
- 将敏感字段改成自由文本、添加姓名/联系方式/精确地址等超范围数据。
- 查看、列出、搜索、导出或删除普通用户匿名记录。
- 修改历史已发布版本的内容；历史版本只读。

如果对可评分字段新增枚举选项，则同一草稿版本必须同时提供该选项的评分值；不能通过固定 `p=1` 或漏掉 score 来绕过校验。

### 5.5 版本与发布

- 一次后台发布生成不可变 `configBundleVersion`，并绑定新的 `catalogVersion`、`modelVersion`；汇率有变化时再绑定新的 `fxVersion`。
- 编辑只发生在草稿副本，发布通过服务端原子切换“当前激活版本”指针；用户不会读到半套新旧配置。
- “回滚”是把当前激活指针切回一个完整的旧版本，不是修改或删除历史版本。
- 新建匿名测试使用发布时的当前版本；已经开始的草稿继续固定在其原版本，避免填写中途选项含义变化。
- 后端保存匿名快照时按快照声明的完整配置包重新计算；版本不存在、checksum 不符或已不受支持时拒绝保存，不信任客户端计算结果。
- 所有已被未过期匿名快照或本机草稿引用的配置版本，至少保留到最长记录保留期结束。
- 审计元数据只记录配置版本、操作类型、时间、Cognito `sub` 和 checksum，不记录匿名答卷内容。

### 5.6 建议的服务隔离

- 现有匿名 Record API 保持单独 Lambda 与最小 DynamoDB 权限。
- 新增只读 Config API，普通用户只可读取当前或指定历史配置包。
- 新增 Admin Config API，只有它拥有创建配置草稿、写入版本和切换激活指针的权限。
- 配置正文建议保存在私有、启用版本控制的 S3 bucket；DynamoDB 仅保存版本元数据、激活指针和发布审计。Excel 原文件默认不上传、不保留。
- CloudFront 对配置读取遵循版本化缓存；“当前激活指针”使用短缓存或 revalidation。管理 API 与匿名记录 API继续 `no-store`。
- 新增资源不能顺带获得读取匿名记录表的 IAM 权限。

## 6. Excel import / export

### 6.1 文件格式

- 首轮只接受 `.xlsx`；明确拒绝 `.xlsm`、宏、外部链接和旧二进制 `.xls`。
- Excel 是配置交换格式，不是运行时直接读取的数据库。
- 导入时只读取单元格值，不执行公式、宏或外部数据连接。
- 原上传文件只在管理员浏览器中解析，默认不上传或覆盖；导出永远生成一个新文件。
- 建议上限：5 MiB、10,000 数据行；超限在解析前拒绝。

### 6.2 工作簿结构

| Sheet | 主要列 | 用途 |
|---|---|---|
| `README` | 只读说明 | 模板版本、比例口径、ID 规则、导入步骤 |
| `Manifest` | `schemaVersion`, `bundleVersion`, `catalogVersion`, `modelVersion`, `fxVersion`, `cityResidualMass`, `status`, `notes` | 标识完整配置包及不可选城市余量 |
| `Cities` | `cityId`, `label`, `titleLabel`, `status`, `isDefault`, `order`, `populationMass` | 真实匹配城市与人口比例；不得放省/大区/其他地区 |
| `Fields` | `fieldId`, `groupId`, `label`, `kind`, `selfControl`, `requirementControl`, `allowedOperators`, `status`, `order`, `sensitive`, `scoreEnabled`, `scoreWeight` | 问题定义；可增加新行，已发布 ID/kind 不可改写 |
| `Options` | `fieldId`, `optionId`, `label`, `enabled`, `order`, `populationMass`, `scoreValue` | 枚举/标签选项及对应比例 |
| `NumericBuckets` | `fieldId`, `bucketId`, `from`, `toExclusive`, `mass` | 数值字段分布 |
| `Presets` | `fieldId`, `presetId`, `label`, `operator`, `value`, `min`, `max`, `valuesCsv`, `order`, `enabled` | 普通与集合预设 |
| `RelativePresets` | `fieldId`, `presetId`, `label`, `comparison`, `offset`, `minOffset`, `maxOffset`, `order`, `enabled` | 相对条件预设 |
| `ScoreKnots` | `fieldId`, `value`, `score`, `order` | 数值评分折点 |
| `ReachTiers` | `tierId`, `label`, `people`, `isDefault`, `order`, `enabled` | 可触达圈层 |
| `ReachBoosts` | `boostId`, `label`, `incrementRate`, `order`, `enabled` | 助力开关与增幅 |
| `StrictnessLevels` | `levelId`, `label`, `coefficient`, `order`, `isDefault` | 五档放宽 |

比例在文件中统一使用 `0～1` 小数，例如 20% 写为 `0.2`；后台预览同时显示百分比，避免把 `20` 误解为 `20%`。

### 6.3 导入流程

1. 管理员选择 `.xlsx`；浏览器只解析允许的 sheet 与列。
2. 先做结构、安全和类型校验，不产生任何服务端写入。
3. 浏览器把规范化 JSON 与文件 checksum 发给 Admin Config API；服务端使用同一套 schema 再校验和计算派生结果。
4. 后台展示差异：新增、修改、停用、比例变化、评分变化及受影响字段。
5. 有任一错误时整次导入失败，并精确显示 `sheet / row / column / errorCode`；不允许部分成功。
6. 通过后只创建“配置草稿”，不会自动发布。
7. 管理员再次确认“发布”后才原子激活新配置包。

### 6.4 必须校验

- ID 格式、唯一性、引用完整性与历史 ID 不可改名；新问题必须使用从未发布过的新 ID。
- 新问题只能使用受支持的字段模板与运算符组合；已发布问题只能 active/retired，不能以删除行的方式抹去历史定义。
- 每个可用字段必须有有效控件、选项/桶与非空分布，不允许用统一 `p=1` 填充缺项。
- 互斥枚举与数值桶的 active mass 总和为 1；全部 active 真实城市质量加 `cityResidualMass` 后为 1，容差建议 `1e-6`。
- 独立标签每项在 `[0,1]`，不要求合计为 1。
- 数值桶有序、不重叠、覆盖字段支持范围，质量非负且合计为 1。
- preset 只引用存在且启用的 option；数值端点在字段范围内，`min <= max`。
- score 在 `[0,100]`；启用评分的字段权重大于 0；自身与对方不能有两套评分表。
- 城市恰好一个默认可选项；所有可选城市质量大于 0，且每个可选项必须对应真实城市。不可选 residual 桶不得出现在普通用户列表或标题中。
- 可触达圈层人数为正整数，恰好一个默认项；助力增幅为有限非负小数。
- 放宽档位恰好五个、系数严格递减、默认档为 1，两个端点固定为 1 和 0。
- 整份规范化配置可被前后端共享引擎加载，所有标准算例、单调性和 round-trip 校验通过。

### 6.5 导出保证

- 可导出当前线上版、任一历史版或当前草稿。
- 文件名包含配置包版本与 UTC 时间，不覆盖管理员导入的原文件。
- 导出后不修改任何业务状态。
- “导出 → 不修改 → 再导入”的规范化 JSON checksum 必须一致；Excel 样式差异不影响 round-trip 判定。

## 7. 可触达圈层与助力

### 7.1 页面与初始选项

结果页新增“你的可触达圈层”区块。圈层必须单选，助力可以多选 toggle；每次变化即时预览，但点击“应用到本次结果”后才写入正式草稿并自动保存。

已确认的首版中性名称与人数：

| `tierId` | 页面名称 | 基础人数 | 默认 |
|---|---|---:|---|
| `daily` | 日常圈 | 2,000 | 是 |
| `extended` | 拓展圈 | 5,000 | 否 |
| `citywide` | 城市圈 | 10,000 | 否 |

已确认的演示助力值：

| `boostId` | 页面名称 | 对基础圈层的固定增幅 |
|---|---|---:|
| `friends` | 朋友助力 | +50% |
| `family` | 家庭助力 | +25% |
| `matchmaking_service` | 相亲服务助力 | +100% |

三个 toggle 可同时开启。增幅以基础圈层为共同基数相加，不连乘，避免开关顺序影响结果。例如日常圈同时开启朋友与家庭助力：`2,000 × (1 + 0.50 + 0.25) = 3,500`。

### 7.2 计算口径

设：

- `B`：全球演示基数。
- `a`：成年人比例。
- `c`：所选匹配城市人口质量。
- `p_i`：第 i 项原条件按现有算法得到的覆盖率。
- `s_i`：第 i 项约束强度。
- `R0`：选中圈层的基础人数。
- `b_j`：已开启助力项的固定增幅。

同城成年人基数：

```text
N_city = B × a × c
```

第 i 项应用五档强度后的有效覆盖率：

```text
e_i = 1 - s_i × (1 - p_i)
```

综合条件覆盖率与同城条件池：

```text
F = ∏ e_i
N_condition = N_city × F
```

有效可触达规模与圈层内候选：

```text
R_effective = min(N_city, R0 × (1 + Σ b_j))
N_reachable = R_effective × F
            = N_condition × R_effective / N_city   (N_city > 0)
```

解释：先计算同城人群中综合条件的覆盖比例，再把同一比例应用到个人可触达的成年人样本中。城市比例只应用一次；不会把“自己住在该城”和“对方住在该城”重复相乘。

### 7.3 结果呈现

结果页同时并列保留两个数字，不互相替代或冒充：

1. **同城条件池**：该匹配城市内按演示模型估算的总体规模。
2. **圈层内预计可触达**：选择圈层和助力后，个人可触达范围内的演示期望规模。

桌面端可并排显示两张同层级结果卡，手机端依次纵向显示；不得只用圈层数字替换或隐藏同城条件池。旁边持续显示：

- `演示圈层，并非真实好友数或平台用户数`
- `不同助力来源可能重叠，当前演示模型按固定增幅估算`
- 小于 1 时继续显示“预计不足 1 人”，不能显示成现实中的零人。

分享卡默认包含匹配城市、同城条件池、圈层、已开助力、有效可触达规模和圈层内候选；管理员配置的免责声明不可隐藏。

### 7.4 边界情况

- 没有打开助力时，`R_effective = min(N_city, R0)`。
- 助力叠加后超过同城成年人基数时按 `N_city` 封顶，不允许圈层比城市本身更大。
- 同城配置质量为 0、缺失或非有限数时配置不得发布；运行时不能靠显示 0 掩盖配置错误。
- 圈层不是新的候选条件，不参与要求分，也不出现在“已启用条件数”中。
- 各助力来源之间没有真实去重数据；不得把结果写成“实际能认识到 X 人”。

## 8. 五档条件放宽

### 8.1 档位名称

已确认首版使用以下名称和百分比：

| `levelId` | 页面名称 | 系数 `s` | 含义 |
|---|---|---:|---|
| `must` | 必须满足 | 1.0 | 完全执行当前条件 |
| `prefer` | 尽量满足 | 0.8 | 保留 80% 的排除强度 |
| `negotiable` | 可以商量 | 0.6 | 保留 60% 的排除强度 |
| `open` | 宽松考虑 | 0.4 | 保留 40% 的排除强度 |
| `any` | 无要求 | 0.0 | 不执行该条件 |

注意：`s` 是“约束强度”，不是直接乘在人数上的存活率。直接使用 `N × 0.8` 会让“无要求 = 0”得到零人，语义错误，因此禁止这样实现。

例如某条件原覆盖率 `p=0.10`：

| 档位 | 有效覆盖率 `e = 1 - s(1-p)` |
|---|---:|
| 必须满足 1.0 | 0.10 |
| 尽量满足 0.8 | 0.28 |
| 可以商量 0.6 | 0.46 |
| 宽松考虑 0.4 | 0.64 |
| 无要求 0.0 | 1.00 |

该公式确保逐档放宽时人数不下降，且两个端点精确回到“完全执行当前条件”和“无要求”。它也意味着中间档会纳入一部分不满足字面条件的人，因此页面不能再笼统声称所有结果都“符合全部条件”。

年龄等数值条件与放松强度在计算上不冲突，顺序固定为：先根据具体选择计算原覆盖率，再用百分比放松排除强度。例如“25～35 岁”的原覆盖率若为 `p=0.24`，选择“可以商量 / 60%”后得到 `e=0.544`。原 predicate 仍然是 25～35 岁；系统不会暗中把它改写成 23～37 岁。扩大的只是模型中的有效覆盖率，而不是一个可精确陈述的新年龄区间。

因此页面统一说“放松排除强度”或“有效覆盖率扩大”，不能写成“年龄范围已扩大”，也不能展示一个并未实际计算的新端点。这个语义区别必须进入帮助文案和分享卡说明。

### 8.2 交互

- 填写页继续负责定义条件内容，例如“25～35 岁”“硕士及以上”；新启用条件默认 `必须满足 / 1.0`。
- 结果页新增“条件松紧度”列表，列出所有已设置 predicate 的条件，每行显示当前条件摘要、五档 segmented control 和该行变化后的结果。
- 未设置 predicate 的字段保持“无要求”，不在默认列表中；可展开“其他条件”查看，但必须返回填写页选定具体条件后才能提高强度。
- 匹配城市、成年人范围、可触达圈层和助力项不属于这五档条件。
- 多个条件可在同一个预览草稿中调整；页面同时显示“已应用结果”和“预览结果”，禁止把多行各自的增量简单相加。
- `应用这些调整` 才写入正式草稿并触发自动保存；`放弃预览` 恢复到已应用值。离开结果页前仍有未应用预览时给出非阻塞提醒。
- 保留“影响最大的三项”快捷区，但每条建议只把一个字段调到相邻的下一档，并进入预览；不直接保存。
- 设置为 `无要求 / 0` 时保留上一次 predicate，便于恢复；计算 trace 中该项的有效覆盖率为 1，已启用要求数不计它。
- 相对条件在 `s>0` 时仍要求自身依赖值；依赖缺失则结果为阶段性。若设置为 `s=0`，该条件不参与计算，也不阻塞完成。

### 8.3 与现有条件算法和评分的关系

- `p_i` 的计算保持现有逻辑：枚举并集去重、数值桶、标签 `any_of`、相对条件解析都不改变。
- 已确认五档只把原始 `p_i` 转成有效覆盖率 `e_i`，不会偷偷改年龄端点、金额门槛或类别集合。
- trace 必须同时返回 `rawCoefficient=p_i`、`strictness=s_i`、`effectiveCoefficient=e_i`，便于前后端解释和复算。
- 要求分仍由原 predicate 投影到同一评分函数；`0 < s <= 1` 不另乘强度，避免把评分再次乘入人数。`s=0` 时该条件从要求分分母移除。
- 当前版本不实现“实际扩大年龄区间/增加类别”。若未来另行增加具体范围扩展，必须写明每个字段的映射，并与本公式择一使用，否则会重复放宽。

## 9. 合并算例（全部为演示值）

假设：

- `B = 8,000,000,000`
- `a = 0.70`
- 东京同城质量 `c = 0.002`
- 性别原覆盖率 `p1 = 0.495`，强度 `s1 = 1.0`
- 年龄原覆盖率 `p2 = 0.24`，强度 `s2 = 0.6`
- 日常圈 `R0 = 2,000`
- 开启朋友助力 `b1 = 0.50`

则：

```text
N_city = 8,000,000,000 × 0.70 × 0.002 = 11,200,000
e1 = 1 - 1.0 × (1 - 0.495) = 0.495
e2 = 1 - 0.6 × (1 - 0.24) = 0.544
F = 0.495 × 0.544 = 0.26928
N_condition = 11,200,000 × 0.26928 = 3,015,936
R_effective = 2,000 × (1 + 0.50) = 3,000
N_reachable = 3,000 × 0.26928 = 807.84
```

页面可显示“东京同城条件池约 302 万人”“日常圈＋朋友助力内约 808 人”，并同时标注这是独立系数演示结果，不是真实统计。

新快照建议升级为 schema v2，核心形态如下；最终 TypeScript 契约在实装阶段按本文确认结果确定：

```json
{
  "schemaVersion": "2.0.0",
  "configBundleVersion": "bundle-demo-2.0.0",
  "catalogVersion": "catalog-demo-2.0.0",
  "modelVersion": "model-demo-2.0.0",
  "fxVersion": "fx-demo-1.0.0",
  "matchCityId": "jp_tokyo",
  "own": {},
  "requirements": {
    "age": {
      "predicate": { "op": "between", "min": 25, "max": 35 },

    "tierId": "daily",

```

由于管理员可以新增问题，v2 不能再把全部业务 `fieldId` 固定为编译期枚举。`fieldId` 在边界层仍是受格式限制的字符串，但必须在快照绑定的 catalog 中存在；共享引擎按 catalog 的字段定义和顺序解释它。保留少量系统保留键（例如城市基础步骤），但不能要求每新增一道普通问题都重新发布前端、Lambda 和 TypeScript union。

服务端复算结果增加：

- `cityAdultBase`
- `conditionCoverage`
- `cityCandidatePool`
- `baseReach`
- `effectiveReach`
- `reachableCandidateCount`
- 含原始比例、约束强度和有效比例的 trace
- `configBundleVersion` 与 checksum

建议 API：

| 方法与路径 | 鉴权 | 用途 |
|---|---|---|
| `GET /api/v2/config/active` | 无登录 | 获取当前激活配置包 |

| `POST /api/admin/v1/configs` | Cognito admin scope | 创建配置草稿 |
| `PUT /api/admin/v1/configs/{version}` | Cognito admin scope | 以 revision/CAS 更新未发布草稿 |
| `POST /api/admin/v1/configs/{version}/publish` | Cognito admin scope | 原子发布 |

## 11. 失败与降级

- 普通用户无法获取当前配置时：已有草稿优先使用其已缓存且 checksum 正确的固定版本；新测试可使用随前端打包的已验证 fallback 版本，但必须显示实际版本，不能伪称取到了最新后台配置。
- 指定历史配置已不可用时：保留本机原数据，提示该版本暂不能复算/上传，不把结果标为已保存。
- 管理员登录失效时：未提交编辑保留在当前页面内，写请求返回 401/403 并要求重新登录；不得降级为匿名写权限。
- Excel 解析、服务端校验、草稿保存和正式发布是四个独立状态；前一步成功不代表后一步成功。
- 发布失败时旧激活版本继续服务；不能出现没有 active 配置的中间状态。
- 线上配置读取异常不能阻止已经加载有效配置的本机计算、结果预览和 PNG 导出。

## 12. 验收标准

### 12.1 同城

- 新测试默认清楚显示东京，切换上海后所有页面标题立即变为“上海·爱情故事”。
- 普通用户的城市选择器只出现真实城市；省、大区和 residual 质量桶永远不成为可选项或标题。
- 普通问卷不再出现现居地卡；快照中不存在重复 `residence` 筛选。
- 城市比例在 trace 中恰好出现一次；切换城市只改变城市基数，不清空其他答案。
- 城市不能设为无要求，也不能进入五档放宽。

### 12.2 管理员与匿名用户

- 未登录用户可完整使用普通估算与匿名保存，但访问管理 API 得到 401/403。
- 管理员登录后只能管理配置，不能通过后台列出或读取匿名记录。
- Cognito 自助注册关闭；无 admin scope 的有效 token 仍不能写配置。
- 首版管理员可在没有 MFA 的情况下按受控邀请流程登录；普通用户仍完全不接触 Cognito。
- 应用日志不包含 token、密码、Excel 内容或匿名请求 body。

### 12.3 配置与 Excel

- 管理员可新增一道受支持类型的问题，并配置其选项、分布、预设和可选评分；发布后新测试能显示并计算该问题，不需要再次修改应用代码。
- 管理员可把已发布问题在新版本标为 retired；新测试不再显示它，旧配置和历史快照仍能解释它。
- 管理员可修改每一种字段分布、选项和对应评分，并在发布前看到结构化差异。
- 任一分布不完整、合计错误、引用不存在或五档不单调时禁止发布。
- 导入错误能定位到 sheet/row/column，且不会产生半套草稿。
- 一个有效工作簿可完整 round-trip；checksum 不因纯格式变化而改变。
- 发布后新测试使用新版本，已开始草稿仍使用旧版本，服务端均能按各自版本复算。

### 12.4 圈层

- 三个圈层可单选，三个助力可独立或同时 toggle。
- 助力增幅以基础圈层相加，结果与开关点击顺序无关，并受同城成年人规模封顶。
- 无条件时圈层内候选等于有效可触达规模；增加/加强任一条件不会让人数增加。
- 同城条件池不因切换圈层或助力而改变；圈层结果会按公式改变。
- 结果页和分享卡都正确显示同层级的“同城条件池”与“圈层内预计可触达”，以及圈层、助力和演示免责声明。

### 12.5 五档放宽

- 每个已设置条件都有五档，新增条件默认 1.0；0 档等价于该项不参与人数计算。
- 对同一 predicate，强度从 1 → 0.8 → 0.6 → 0.4 → 0 时人数单调不减。
- 所有条件均为 1 时，除现居地已迁移为城市基数外，人数与现有硬筛选算法一致。
- 所有条件均为 0 时，同城条件池回到同城成年人基数，圈层内候选回到有效可触达规模。
- 多项预览不写入正式草稿；应用后才保存。预览增量不允许逐项相加。
- 自身分、要求分、同城条件池、圈层内候选四个概念分别展示，不互相替代。

### 12.6 验证层级

实装后报告必须分别说明：

1. 设计/契约已更新。
2. 本机实现与单元、集成、浏览器测试结果。
3. CDK synth/diff 结果及 Cognito、S3、DynamoDB、API 增量与费用影响。
4. 获得单次部署授权后才可报告真实 AWS 验证。
5. 部署后真实管理员登录、导入/发布与公网匿名流程验证。

没有 AWS 账户、管理员邮箱或部署授权时，不影响本地实现，但不能报告真实服务或线上验证完成。

## 14. 已确认决策

### 14.1 已确认

1. 普通用户只能选择真实城市，例如东京、上海、北京、大阪；不显示省、大区或“其他地区”。默认城市仍为东京。
2. 五档保持具体 predicate 不变，按 `e = 1 - s(1-p)` 放松排除强度；不生成虚构的新年龄端点或新增类别。
3. 助力以基础圈层为共同基数做加法叠加，不连续相乘。
4. 初始助力为朋友 +50%、家庭 +25%、相亲服务 +100%。
5. 结果同时显示“同城条件池”和“圈层内预计可触达”，不互相替代。
6. 管理员可以新增问题；尚未发布的问题可删除，已发布问题在新版本中 retired，历史版本保留。
7. Cognito 管理员首版不要求 MFA；继续关闭自助注册并只允许受控邀请。
8. Excel 使用 `.xlsx`，现有草稿固定旧配置版本，后台不读取匿名答卷。

### 14.2 五档不影响“对方要求分”的已确认口径

这里有两个彼此独立的量：

- **人数估算**回答“在当前条件强度下，大约覆盖多少人”。五档已经确认影响这个量。
- **对方要求分**回答“所填写的条件本身对应什么门槛”。当前模型不是“重视程度分”。

例如“年收入至少 24 万元”在统一评分函数中投影为 70 分：

- 选 `必须满足 / 1.0`：人数按原收入覆盖率计算，收入门槛分为 70。
- 选 `宽松考虑 / 0.4`：人数按放松后的有效覆盖率计算，但具体门槛仍是“至少 24 万元”，因此收入门槛分仍为 70。
- 选 `无要求 / 0`：该项不再是要求，从要求分的分子和分母中一起移除。

已确认保持上述规则，即 **0.4～1.0 只影响人数，不改变要求分；0 才移除评分项**。理由是这样能继续保证自身和对方使用同一个评分函数，也不会把“门槛高低”和“有多在意”混成一个数。

如果把强度用于评分，还必须另外决定算法：

- 把字段权重乘以 `s`，只会改变它相对其他字段的重要性；若只有这一项，归一化后的总分仍可能是 70。
- 把字段分数直接乘以 `s`，则 70 分在 0.4 档会变成 28 分，但这破坏“相同条件使用同一评分函数”的现有口径，指标也应改名为“综合要求指数”。

实现必须采用 `0.4～1.0 不改变要求分，0 档移除该项`，不得另行把强度乘入要求分。
